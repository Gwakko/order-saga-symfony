# M6.3. Отмена, компенсации, возврат

## Сделано
- **Сигнал и guard.** `OrderFulfillmentWorkflow::requestCancellation()` (`#[SignalMethod]`) ставит флаг. `guardCancellation()` (флаг сигнала ИЛИ активность `IsCancellationRequested`, то есть флаг в БД) выполняется перед первым шагом, перед `ChargePayment` и перед `ConsumeReservation`. После `ConsumeReservation` отмена игнорируется. Первый guard (ничего не сделано) -> `CancelOrderBeforeStart` -> `Cancelled`; остальные -> `StartOrderCompensation(CancelledByCustomer)` -> компенсации -> `FinishOrderCompensation` (`Cancelled`). Внутреннее исключение `CancellationRequested`.
- **Активности:** `IsCancellationRequested`, `CancelOrderBeforeStart`, `FinishOrderRefund` (`OrderActivities`), `RevokeSoldKey` (`InventoryActivities`).
- **`TemporalOrderSagaSignals`** вместо `LoggingOrderSagaSignals` (файл удалён, алиас порта в `config/services.yaml`). `WorkflowNotFoundException` (workflow ещё не запущен или уже завершён) считается нормой: `CancelOrder` сначала фиксирует флаг в БД, затем сигналит, поэтому запущенный позже workflow увидит флаг в первом guard, а уже запущенный получит сигнал. Остальные ошибки (Temporal недоступен) пробрасываются, `CancelOrderHandler` логирует `warning` и отвечает 202.
- **Компенсации** (`Saga`, последовательно): `RefundPayment`, затем `ReleaseReservation`; сбой компенсации -> `MarkOrderManualReview` и `return 'ManualReview'` без исключения. Логика идемпотентности (`PaymentRefunder`: `Succeeded`/`RefundPending`/`Pending`+`Unknown` через `findCharge`/`Abandoned`; ключ `refund-{paymentId}`) уже была в M3, здесь подтверждена тестами.
- **`RefundWorkflow`** (`refund-{orderId}`, тип `OrderRefund`): `RevokeSoldKey` -> `RefundPayment` -> `FinishOrderRefund`; сбой шага -> `MarkOrderManualReview` (`Refunding -> ManualReview`). `TemporalOrderRefundStarter` (RejectDuplicate, `WorkflowExecutionAlreadyStartedException` = успех), потребитель `StartOrderRefundOnOrderRefundStarted` (inbox, потребитель `start_order_refund`), порт `Ordering\Application\Port\OrderRefundStarter`. Воркеры (`bin/temporal-worker.php`, `tests/Workflow/worker.php`) регистрируют `RefundWorkflowImpl`.
- **ManualReview**: статус, событие `OrderNeedsManualReview` (reason, step), лог `critical` (handler был в M3.3); workflow после него завершается, повторов нет. Отдельной таблицы «для оператора» нет: запись оператора = статус + событие (в outbox/проекции) + лог, как в `03_saga.md` §4.
- Конфиг: профиль `revoke_sold_key`, параметр `temporal.refund_workflow.execution_timeout_seconds`, `SagaConfiguration::refundWorkflowOptions()`.

## Отклонения
1. **Execution timeout обоих workflow 8 суток** (`691200` с) вместо 24 ч / 7 сут из `03_saga.md` §1. Причина: `RefundPayment` как компенсация имеет ScheduleToClose 7 суток (§3), и workflow с 24-часовым лимитом был бы убит Temporal раньше, чем сага перевела бы заказ в `ManualReview` (EC-47). У `RefundWorkflow` 7 суток равны ScheduleToClose шага без запаса. Параметры `temporal.order_workflow.execution_timeout_seconds`, `temporal.refund_workflow.execution_timeout_seconds`; проверяет `SagaConfigurationTest::testRunTimeoutsOutlastTheLongestCompensation`.
2. **Порядок компенсаций и упавший refund.** `Saga` останавливается на первом сбое (без `continueWithError`), поэтому после непрошедшего `RefundPayment` `ReleaseReservation` не выполняется, а резерв освободит TTL/sweeper (`ExpireReservations`). Это следует из §4 («при параллели ключ может вернуться в продажу раньше, чем выяснится, что refund невозможен»), но в спеке явно не сказано.
3. **Guard через сигнал не читает БД**: если флаг сигнала уже стоит, активность `IsCancellationRequested` пропускается (в истории меньше событий). Если сигнал потерян, активность читает флаг из БД (§2).
4. **`IsCancellationRequested`** читает `OrderRepository::get()->cancellationRequested` прямо в реализации активности (как `ReserveKey` читает `productId`), а не через query-handler: отдельный handler для одного булева значения избыточен.
5. **Новый порт `OrderRefundStarter`** (Ordering/Application/Port): единственное добавление в application-слой; потребитель живёт в `Saga\Infrastructure`, как у старта саги. Domain не менялся.
6. **Профиль `revoke_sold_key`** (в таблице §3 для `RevokeSoldKey` строки нет): 5 с / 1 мин, повторы как у `MarkOrder*`, non-retryable `ReservationNotFound` и `KeyNotFound`. Для `RefundPayment` внутри `RefundWorkflow` использован профиль компенсации (7 суток), для `FinishOrderRefund`/`MarkOrderManualReview` профиль `order_step`.
7. **EC-36/37** (расхождение валюты/суммы) закрывает `OrderFulfillmentWorkflow`, а не `RefundWorkflow`: `ChargePayment` падает non-retryable (`CurrencyMismatch`/`AmountMismatch`), платёж уже `RefundPending` (`markCapturedWithMismatch`, M3.3), компенсация `RefundPayment` делает refund, итог `Failed(CurrencyMismatch)`. Покрыто T-U-35/36 и T-W-08; `RefundWorkflow` нужен только для возврата после выдачи ключа.
8. **`SagaConfiguration`**: добавлен последний необязательный параметр `refundWorkflowExecutionTimeoutSeconds` (чтобы не ломать существующие вызовы).
9. **Типы в `OrderFulfillmentWorkflowImpl`**: приватные методы получают заглушку активности как `object` + `@param ActivityProxy<OrderActivities>` (PHPStan max не принимает `ActivityProxy<T>` как `T`).
10. **T-I-24** использует реального воркера, запускаемого тестом (`tests/Integration/Support/TemporalTestWorker`: `rr serve -c .rr.yaml -o rpc.listen=tcp://127.0.0.1:6002`, `APP_ENV=test`). Эмулятор не считает отклонённые 503 запросы в `stats`, поэтому число попыток берётся из истории workflow (`ActivityTaskStarted.attempt`).
11. **T-F-12**: outbox relay и Messenger не поднимаются; тест берёт сообщение `OrderRefundStarted` из таблицы outbox и вызывает потребитель напрямую (как T-I-20). Для воркера нужен `rr` и порт 6002 в контейнере `php`.
12. **Тесты T-W с реальным временем**: T-W-10 (сигнал), -11, -12, -13, -14 запускают `lockTimeSkipping()` и ждут второй/третью попытку активности (до 15 с для T-W-14). Набор workflow ~25 с против ~3 с раньше.
13. Файл `LoggingOrderSagaSignals` удалён (замена по спеке M6.3), документация M5 на него ссылается как на временную.
14. Правок `compose.yaml` и CI нет. CI-шаг `test-int` теперь требует `rr` (он уже установлен для `test-wf`) и `ext-grpc` для T-I-24/T-F-12; в GitHub-прогоне не проверялось (как и в M6.2).
