# M4.6. Read model, сверка, JSON-сериализация outbox

## JSON-сериализация outbox (решение пользователя, сделано в начале M4.6)
- Колонка `outbox_messages.payload` уже была `jsonb` с JSON из нормализаторов, поэтому миграция схемы не понадобилась (проверка вверх-вниз-вверх не требуется). Менялся только формат сообщения в Redis Stream: был PHP `serialize()` (в том числе внешний слой phpredis), стал JSON.
- `config/packages/messenger.yaml`: `serializer.default_serializer: messenger.transport.symfony_serializer` (Symfony Serializer, формат json, заголовок `type` и `Content-Type: application/json`). В `.env` DSN `redis://redis:6379?serializer=0`: отключает PHP-сериализацию самой записи в stream (опция `options.serializer` в YAML не годится: фреймворк трактует её как сервис). Запись в stream теперь читаемый JSON `{"body": "{...}", "headers": {...}}`.
- `EventNormalizer` получил обратные методы `supportsMessage()` и `denormalize(OutboxMessage): DomainEvent`; реализованы в `OrderEventNormalizer`, `InventoryEventNormalizer`, `PaymentEventNormalizer`. Новый `DomainEventCodec` (`toMessage`, `toEvent`). Домен без атрибутов и без изменений.
- Событие без payload пишется в БД как `{}` (раньше `[]`).
- Тесты (`tests/Integration/Messaging`): `DomainEventRoundTripTest` (событие -> `OutboxMessage` -> JSON транспорта -> `OutboxMessage` -> событие, `assertEquals` для всех 21 конкретных событий, два варианта `KeyRevoked` и `PaymentCapturedWithMismatch`; микросекунды сохраняются; деньги целые; код ключа `ZXCV-QWER-7391` нигде в JSON, только маска; тест, что набор образцов покрывает каждый класс из `src/*/Domain/Event` (новое событие без нормализатора ломает тест); путь через `OutboxWriter` -> строка БД -> relay -> событие). Образцы: `tests/Support/DomainEventSamples.php`. `OutboxRelayCommandTest` и `MessengerFailureTransportTest` теперь проверяют, что в stream лежит JSON, а не `serialize()`.
- Прежние тестовые сообщения M4.3 (`MessengerFailureTransportTest::message`) получили тип агрегата `test` вместо `order`: иначе проекция заказа (теперь реальный потребитель) правомерно падала бы на выдуманном payload.
- Старые сообщения в stream в формате `serialize()` (если остались в dev) новым потребителем не читаются; очистить `redis-cli DEL domain_events domain_events_failed`.

## Сделано
- `OrderProjection` (`Ordering/Infrastructure/Projection`, `#[AsMessageHandler]`, `InboxGuard::once('order_projection', ...)`): `OrderPlaced` вставляет строку `order_view`, остальные события обновляют `WHERE version < :v` (EC-55, INV-15); устаревшее подтверждается без эффекта. Событие раньше `OrderPlaced` бросает `OrderViewNotReady` (Messenger повторит, строки inbox нет).
- `DbalOrderReadModel`: `find` (код ключа только при `completed`, из `product_keys` по `delivered_key_id`), `list` (`created_at DESC, order_id DESC`, строгий keyset `(created_at, order_id) < (...)`, фильтр статуса).
- `DbalProductReadModel` над `product_availability_view`; `ProductAvailabilityProjection` (пересчёт `available` и upsert при каждом событии резервации/ключа, идемпотентен и не зависит от порядка; метод `refresh(ProductId)`).
- Консольные команды `app:reservations:expire` (`--limit`) и `app:payments:reconcile` (`--older-than`, `--limit`), ошибка диапазона даёт код 2.
- Scheduler (`src/Schedule.php`): `ExpireReservationsTick` каждые 30 с, `ReconcilePaymentsTick` каждые 5 мин; свои сообщения и обработчики вызывают те же application-обработчики (`RunCommandMessage` не годится: в Symfony 8.1 его обработчик требует подписанного сообщения). `debug:schedule` показывает оба задания.
- `compose.yaml`: сервисы `outbox-relay`, `messenger-consumer` (`messenger:consume domain_events`), `scheduler` (`messenger:consume scheduler_default`), профиль `workers` (`docker compose --profile workers up -d`).

## Тесты
- T-I-34 `OrderProjectionTest::testStaleVersionIgnored` (v1, v3, потом v2: статус `paid`, версия 3). Рядом: повтор сообщения (inbox), событие раньше `OrderPlaced`, чужой тип агрегата, обратный порядок, и для 12 жизненных циклов (`OrderFactory`) строка `order_view` совпадает с агрегатом по всем полям.
- T-I-21 `ReconcilePaymentsTest::testLateSuccessIsRefunded` (Postgres + настоящий эмулятор: платёж `Abandoned`, заказ `Failed`, списание есть у шлюза: `Refunded`, один возврат, `OrphanChargeDetected` и `PaymentRefunded` в outbox); повторный запуск, отсутствие списания, недоступный шлюз.
- Сравнительный тест `OrderReadModelContractTest`: `DbalOrderReadModel` и `InMemoryOrderReadModel` дают равные результаты для 3 клиентов, всех статусов и без, лимитов 1/2/3/5/100, всех позиций курсора (ничья по `created_at`, микросекунды, чужой клиент).
- `ProductAvailabilityTest`, `MaintenanceCommandsTest`, `ScheduleTest` (unit), `ProjectionEndToEndTest` (репозиторий -> outbox -> relay -> Redis -> `messenger:consume` -> `order_view`).
- `make ci` зелёный; цикл `--group concurrency` 20 из 20.

## Не сделано
- `AddProductKeys` и создание товара не порождают событий, поэтому `product_availability_view` для нового товара пуста до первого события резервации (или вызова `ProductAvailabilityProjection::refresh`). Нужен вызов `refresh` из `AddProductKeys` или команда наполнения (M5/seed).
- Нет теста на живой процесс `outbox-relay` в compose (проверен `--once` и `debug:schedule` в контейнере).

## Отклонения
- Дефект найден и исправлен в инфраструктуре: `DbalPaymentRepository::save` писал в outbox все `pendingEvents`, а `ChargeRecorder`/`PaymentRefunder` продолжают работать с тем же агрегатом после `save` (record -> requestRefund -> markRefunded), поэтому повторная запись давала `duplicate key outbox_messages_pkey` на настоящей БД (юнит-тесты на in-memory этого не видят). Теперь пишутся только события версии `>= payment.version`; регрессионный тест `DbalPaymentRepositoryTest::testContinuingASavedAggregateDoesNotRepublishEarlierEvents`. Аналогичный шаблон есть в `DbalKeyInventory::save` и `DbalReservationRepository::save`; их обработчики перечитывают агрегат, поэтому сейчас не проявляется, но стоит выровнять.
- Потеря флага `cancellation_requested` при обгоне: `OrderCancellationRequested` (v2), пришедший после v3, игнорируется по версии, и флаг в `order_view` не выставится (при `OrderCancelled` выставляется всегда). Принято: порядок гарантируется relay (`occurred_at, aggregate_version`), обгон возможен только при повторах.
- Воркеры compose не стартуют по умолчанию (профиль `workers`): интеграционные тесты делят БД и Redis с dev, работающий relay уводил бы строки outbox из-под тестов.
- Сообщения Scheduler свои, а не `RunCommandMessage` (см. выше).

## Что проверить вручную
- `docker compose --profile workers up -d` и сквозной прогон: создать заказ в БД, посмотреть `order_view`, `docker compose logs messenger-consumer`.
- `redis-cli XRANGE domain_events - + COUNT 1`: тело читается как JSON.
- `bin/console messenger:failed:show` после искусственного падения проекции.
