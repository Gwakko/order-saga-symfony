# M4.2. DBAL-репозитории и транзакции

## Сделано
Shared (`src/Shared/Infrastructure`):
- `Persistence/DbalTransactionManager`: реентерабельный (внутри открытой транзакции просто вызывает callback, внешний вызов коммитит или откатывает), поэтому репозиторий сам атомарен и внутри use case, и вне его.
- `Persistence/DbTimestamp`, `Persistence/Row`: UTC-форматирование `timestamptz` и типизированное чтение строк DBAL (одно место сужения `mixed`).
- `Id/SymfonyUuidGenerator` (UUID v7), `Psr\Clock\ClockInterface` = `NativeClock('UTC')` в `config/services.yaml`.

Репозитории и адаптеры портов:
- `Ordering`: `DbalOrderRepository` (CAS `stored = version - count(pendingEvents)`, 0 = INSERT), `OrderEventNormalizer`, `DbalOrderPriceReader`, `DbalOrderOutcomeReader`.
- `Inventory`: `DbalKeyInventory` (`FOR UPDATE SKIP LOCKED`, требует открытую транзакцию, `addIfAbsent` через `ON CONFLICT DO NOTHING`, CAS `version-1`), `DbalReservationRepository` (version 1 = INSERT, иначе CAS; `findByOrder` предпочитает живую резервацию), `DbalProductCatalog`, `DbalDeliveredKeyReader`, `DbalReservationStatusReader`, `InventoryEventNormalizer`.
- `Payment`: `DbalPaymentRepository` (`insertOrGet` через `ON CONFLICT DO NOTHING` и перечитывание по `order_id`; CAS `stored + 1 = version`; `findOpenUpdatedBefore`), `PaymentEventNormalizer`.
- Запись событий в outbox происходит в `save` (в общей транзакции с состоянием); сам outbox описан в M4.3.

Тесты (`tests/Integration/Persistence`, группы `M4.2` + идентификатор из спеки):
- T-I-11 `DbalPaymentRepositoryTest::testConcurrentInsertOrGet` (3 форкнутых процесса, 20 раундов).
- T-I-12 `DbalKeyInventoryTest::testOutOfStock`.
- T-I-13 `DbalKeyInventoryConcurrencyTest::testLastKeyReservedOnce` (50 раундов, 2 процесса; плюс 6 покупателей на 4 ключа).
- T-I-14 `ReservationExpiryFlowTest` (граница `expiresAt` = истекла, sweeper освобождает ключ, ключ можно продать снова).
- T-I-15 `ReservationCasTest::testSweeperVsConsume` (30 раундов; ровно один победитель, ключ и резервация согласованы) + детерминированный тест устаревшей записи.
- T-I-16 `ReserveKeyIdempotencyTest` (повтор после потери ответа; параллельные повторы одного заказа: проигравший откатывает свой ключ).
- T-I-41 `OrderConcurrencyTest` (детерминированная гонка `RaceOnceOrderRepository` в обе стороны + 30 раундов в форках: итог `Paid` и `cancellationRequested=true`, версия 4, по событию на переход).
- Дополнительно: `DbalOrderRepositoryTest`, `DbalReservationRepositoryTest`, `CrossModuleReadersTest`.
- Инфраструктура тестов: `IntegrationTestCase`, `Support/{TestDatabase, ForkedRunner, Infra, RaceOnceOrderRepository}`. `ForkedRunner` форкает процессы со своими соединениями и стартует их по файловому барьеру; ребёнок завершается SIGKILL, чтобы деструкторы унаследованных сокетов не закрыли сессию родителя.

- Цикл `for i in $(seq 20); do vendor/bin/phpunit --group concurrency || exit 1; done` (в контейнере, группа включает T-I-11/13/15/16/41/35): результат см. строку ниже.

**Результат цикла concurrency: 20 прогонов из 20 подряд зелёные** (каждый прогон: 7 тестов группы `concurrency`, ~1000 утверждений; нестабильных падений нет).

## Отклонения от спеки
- Порты не менялись. Домен и application не менялись.
- Конфликт уникального индекса (INV-04/05, `payments(order_id)`) превращён в `ON CONFLICT DO NOTHING` + проверка числа строк, а не в перехват исключения: нарушение уникальности прерывает всю текущую транзакцию Postgres, и use case не смог бы продолжить (например, `insertOrGet` внутри транзакции).
- `DbalKeyInventory::lockAvailable` бросает `LogicException` вне транзакции (блокировка кончается вместе с запросом, это ошибка вызова).
- Изоляция тестов: `TRUNCATE` перед каждым integration-тестом (а не откат транзакции), потому что outbox, форки и транзакции самих репозиториев требуют видимости между соединениями. Эти тесты нельзя запускать параллельно друг с другом на одной БД; для параллели есть `TEST_TOKEN` (суффикс имени БД).
- Тестовая БД `app_test` создаётся и мигрируется самим `TestDatabase::prepare()` (один раз на процесс PHPUnit).
- `save` агрегата с накопленными `pendingEvents` нельзя повторять тем же экземпляром (id события выводится детерминированно, повторная запись упадёт на PK outbox); после `save` нужно перечитать агрегат. Все handlers M3 так и делают, правило записано в тестах.
- Побочный эффект: `php-cs-fixer fix` без путей переформатировал файлы `gateway-emulator/` (M4.4, другой исполнитель этапа): шесть файлов, только стиль. Дальше я запускал его только на `src tests migrations config phpstan`.

## Что проверить вручную
- Нагрузочное поведение `SKIP LOCKED` на реальных объёмах ключей (индекс частичный по `status='available'`).
- Дедлоки: Consume и Sweeper берут блокировки в одном порядке (ключ, затем резервация); цикл из 20 прогонов их не выявил, но других порядков в будущих handlers (M6) нужно избегать.
