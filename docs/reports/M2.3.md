# M2.3 Inventory

## Сделано
- `src/Inventory/Domain`: `Product` (имя 1..200 символов, цена > 0, `assertAvailable` → `ProductUnavailable`), `ProductKey` + `KeyStatus` (таблица §4.2, неизменяемый, `add`/`reconstitute`/`reserve`/`release`/`sell`/`revoke`), `KeyReservation` + `ReservationStatus` (`create`, `consume(OrderId, now)`, `release`, `expire`, граница `now >= expiresAt`), события `KeyReserved`, `KeyReleased`, `KeySold`, `ReservationExpired` (из `KeyReservation`), `KeyRevoked` (из `ProductKey::revoke`), исключения.
- Тесты `tests/Unit/Inventory/Domain` (82): T-U-12 `KeyReservationTest` (таблица 4×4 на двух уровнях, граница `now == expiresAt`, идемпотентные `release`/`consume`, EC-20, EC-22), T-U-13 `ProductKeyTest` (таблица 4×4), `ProductTest`.
- Проверка: `make phpstan PHP=` OK, `vendor/bin/phpunit --filter Inventory` OK.

## Не сделано
- Событие при добавлении ключей (`AddProductKeys`) и согласование статусов ключа и резервации: это работа handler-ов (M3).

## Отклонения от спеки
- События `KeyReserved/Released/Sold/Expired` несёт `KeyReservation` (там есть `orderId`), `KeyRevoked` несёт `ProductKey::revoke(?OrderId, now)`; остальные переходы ключа событий не дают (изменение доступности проекция берёт из событий резерваций).
- `consume` на `Expired` бросает `ReservationHasExpired` (смысл EC-16), а не общий illegal transition; на `Released` или при чужом `orderId`: `IllegalReservationTransition`.
- `expire` до `expiresAt` и повторный `expire` на `Expired`: `IllegalReservationTransition` (таблица идемпотентности для него не задаёт).
- Исключение названо `ReservationHasExpired`, чтобы не конфликтовать с событием `ReservationExpired`.
- `KeyReservation::create` принимает `ttlSeconds` аргументом (конфиг `inventory.reservation_ttl_seconds` читает handler).

## Что проверить вручную
- Название `ReservationHasExpired` против `ReservationExpired` при написании handlers (M3).
