# M7.1 GraphQL: схема и резолверы

## Сделано
- `webonyx/graphql-php` v15.39.0 (в `composer.json` уже `^15.39`, проверено `composer show`; PHP `^7.4 || ^8`).
- `config/graphql/schema.graphql` (SDL, читается при сборке контейнера):
  - `Query { order(id: ID!): Order, myOrders(status: OrderStatus, limit: Int = 20, cursor: String): OrderPage!, product(id: ID!): Product }`. Мутаций нет (U2).
  - `OrderStatus` = значения домена в верхнем регистре (`PENDING`, `KEY_RESERVED`, ... `MANUAL_REVIEW`), `DateTime` (ISO-8601 UTC, мс, как в REST), `Money { amount: Int!, currency: String! }` (минимальные единицы, `MAX_AMOUNT` 1e8 влезает в Int32, float нет).
  - `Order` (все поля `OrderDetailsOutput` + `product`), `OrderSummary` (строка списка, без `keyCode`), `OrderPage { items: [OrderSummary!]!, nextCursor }`, `Product { productId, name, price, available }`.
- `src/Ordering/Infrastructure/GraphQL/`: `GraphQlController` (`POST /graphql`, `CustomerId` тем же `CustomerIdValueResolver`), `GraphQlSchemaFactory` (SDL -> `Schema`, общий сервис контейнера, строится один раз на процесс, `assertValid()`), `QueryResolver` (только аргументы -> query -> `QueryBus`), `OrderFieldResolver` (enum/даты в формате REST, `product` через loader), `ProductBatchLoader` (DataLoader на `Deferred`, один на запрос), `GraphQlContext`, `GraphQlErrorFormatter`, `GraphQlExceptionListener` (ошибки вне исполнения: нет `X-Customer-Id`, битое тело, 405, 413 в GraphQL-форме), `GraphQlValidationRules` (см. M7.2).
- Ошибки: `extensions.code` = те же коды, что у REST; `extensions.status` = HTTP-статус REST. 5xx и неожиданные исключения -> `INTERNAL_ERROR` без текста. Ошибки самой библиотеки (синтаксис, валидация, переменные) -> `GRAPHQL_VALIDATION_FAILED`.
- Общая таблица статусов вынесена из `ExceptionToProblemListener` в `Shared/Infrastructure/Http/ErrorStatusMap` (`statusOf`, `httpCode`); логика `match` не дублируется, поведение REST не изменилось (добавлен только 413 -> `PAYLOAD_TOO_LARGE`).
- Батч-загрузка (EC-84): новый query `GetProductsAvailability` (Inventory/Application) и метод порта `ProductReadModel::findMany` (Dbal: один `IN (...)`; fake обновлён).
- Тесты: `GraphQlQueryTest` (T-F-24 GraphQL, T-F-31), `GraphQlBatchLoadingTest` (T-F-32), unit `GraphQlErrorFormatterTest`, `ProductBatchLoaderTest`, integration `findMany`. Счётчик SQL: `tests/Functional/Support/SqlRecorder` + штатный DBAL logging middleware, зарегистрированный в `services_test.yaml`.
- Курсор: unit-тесты `OrderCursor` уже есть (M4.6, `OrderQueriesTest`); GraphQL-путь курсора покрыт функциональными тестами (проход по страницам, `INVALID_CURSOR`).

## Доказательство отсутствия N+1
`myOrders { items { product { name } } }` на 20 заказах: ровно 1 SQL к `product_availability_view` и 1 к `order_view` (T-F-32, счёт по тексту SQL); unit-тест: любое число `load()` = один вызов use case с уникальными id.

## Отклонения
- Domain/Application: добавлены query `GetProductsAvailability` и `ProductReadModel::findMany` (минимально, нужны для батча).
- Ошибки резолверов идут с HTTP 200 + `data: null/частичные` + `errors[].extensions.status` (конвенция GraphQL), а не с HTTP 404. EC-70: код `ORDER_NOT_FOUND` тот же, свой и чужой заказ неразличимы. Ошибки до исполнения (нет заголовка покупателя 401, битое тело 400, валидация запроса 400, 413) идут с реальным HTTP-статусом.
- Для списка введён тип `OrderSummary` (в спеке только `OrderPage!`), чтобы `keyCode` не мог попасть в список (INV-17).
- `keyCode` возвращается целиком, как в REST, и только у `COMPLETED` (маскирования нет: покупатель получает ключ именно здесь).
- Схема строится один раз на процесс контейнера; под PHP-FPM это каждый воркер-процесс, отдельного кэша AST нет.
- Ограничение тела 16 KiB (в спеке нет, добавлено, M7.2).
