# M5.1. Контроллеры, Request DTO, ошибки

## Сделано
- Шины Messenger `command.bus`, `query.bus` (синхронные) и `event.bus` (шина по умолчанию, на ней работают потребители outbox и Scheduler). Обработчики попадают на шины через `_instanceof` в `config/services.yaml` по маркерам `CommandHandler`/`QueryHandler`, тип сообщения берётся из `__invoke`. Application не тронут.
- `Shared/Infrastructure/Bus`: `CommandBus`, `QueryBus` (общая база `UseCaseBus`, типизированный `execute($message, Output::class)`, исключение обработчика пробрасывается без обёртки `HandlerFailedException`).
- Входящий слой Ordering (`Ordering/Infrastructure/Http`):
  - Request DTO `final readonly` с Assert: `PlaceOrderRequest`, `MoneyRequest` (`#[Assert\Valid]`), `ListCustomerOrdersRequest` (`#[MapQueryString]`). Request превращается в Command/Query методом `toCommand()`/`toQuery()` на границе контроллера.
  - Контроллеры (один action на класс, `final readonly`, без Doctrine и бизнес-логики): `PlaceOrderController` (201 + `Location`, `orderId` генерируется `IdGenerator` до вызова), `CancelOrderController` (202), `RequestRefundController` (202), `GetOrderController` (200), `ListCustomerOrdersController` (200).
  - `PlaceOrderRequest` читается с контекстом `allow_extra_attributes: false`.
- Исходящие данные только через Serializer: `OutputNormalizer` (база) и по нормализатору на каждый Output (`PlaceOrder`, `CancelOrder`, `RequestRefund`, `OrderDetails`, `OrderSummary`, `ListCustomerOrders`, `Money`, `ProblemDetails`). Формат вывода прописан явно. Контроллеры отвечают через `JsonResponder` (`serializer->serialize`), без `json_encode` и без `array`.
- Время ответа: `ApiDateTime` (UTC, `Y-m-d\TH:i:s.vP`, миллисекунды, `+00:00`), используется во всех нормализаторах (EC-76).
- `CustomerId`: `CustomerIdValueResolver` (ArgumentValueResolver) и `CustomerIdHeader` (одно место чтения `X-Customer-Id`; регистр и пробелы нормализуются). Нет или не UUID: `CustomerRequired`, 401.
- `ExceptionToProblemListener` (`kernel.exception`, только `/api`): RFC 9457 `application/problem+json` (`type`, `title`, `status`, `code`, `detail`, `errors[]`, для `PRICE_CHANGED` `currentPrice`). Таблица кодов в одном исчерпывающем `match` по `DomainErrorCode` (без `default`: новый код не скомпилируется молча). Коды без смысла в HTTP (саговые) дают 500 без `detail`. HTTP-исключения Symfony (404 маршрута, 405, 400, 415) получают коды `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `BAD_REQUEST`, `UNSUPPORTED_MEDIA_TYPE`. Любое неожиданное исключение: 500 `INTERNAL_ERROR`, без утечки текста (логируется).
- `LoggingOrderSagaSignals` (Ordering/Infrastructure/Saga): временная реализация порта `OrderSagaSignals`, чтобы собрался `CancelOrderHandler`. До M6.2 только пишет в лог. Флаг отмены уже в БД, workflow читает его перед каждым шагом (03_saga.md §5).
- `config/services_test.yaml`: публичные сервисы для функциональных тестов; `ProductCatalog` в `test` указывает на `SwitchableProductCatalog` (тестовый декоратор, умеет падать).

## Фактическое поведение, которое просила записать спека
- **EC-64j (битый JSON `{"productId":`)**: **400** `BAD_REQUEST`, `detail: Request payload contains invalid "json" data.` (так отвечает `MapRequestPayload`, не 422). Пустое тело тоже 400. Тесты: `PlaceOrderValidationTest` (кейсы `EC-64j`, `empty body`).
- **EC-64i (лишнее поле)**: **422** `VALIDATION_FAILED`, `errors[].propertyPath` = имя лишнего поля (`price`, для вложенного `expectedPrice.scale`). Нюанс: `MapRequestPayload` не превращает `ExtraAttributesException` в нарушение, а пробрасывает его, и без доработки ответ был бы **500**. Исключение отображается в `ExceptionToProblemListener`.
- Неизвестный JSON и лишние поля в остальных случаях: любое лишнее свойство на любом уровне (в том числе `expectedPrice` как число, `"text"` как тело) даёт 422 с путём (`expectedPrice.0`, `0`). `[]`, `{}`, `null`, отсутствующие `productId`/`expectedPrice`/`amount` дают 422 с путями недостающих полей. Для query-строки (`GET /api/orders`) лишние параметры игнорируются (контекст `allow_extra_attributes` задан только для тела).
- Неверный `Content-Type`: `text/plain` и неизвестный тип дают 415 `UNSUPPORTED_MEDIA_TYPE`; `application/x-www-form-urlencoded`, `multipart/form-data` и `text/xml` Symfony пытается разобрать как форму или XML и отвечает 400 `BAD_REQUEST`; запрос без `Content-Type` (клиент шлёт форму по умолчанию) тоже 400.
- Дробное `10.5`, `100.0`, `1e2`, `"100"`, `null`, `true` и `99999999999999999999` в `amount`: 422 («This value should be of type int.», тип не приводится), заказа нет.
- Побочный эффект Symfony: после записи ошибки типа сериализатор всё равно вызывает конструктор DTO сырым значением, и PHP 8.5 выдаёт deprecation `Implicit conversion from float 10.5 to int` (и для `limit=1.5`). Ответ 422 не меняется. В двух тестах поставлен `#[IgnoreDeprecations('Implicit conversion from float')]` с комментарием; в проде это строка в логе deprecation.
- Регистр UUID: `productId` и `orderId` в верхнем регистре принимаются (приводятся к нижнему); `X-Customer-Id` тоже. Неверный `orderId` в пути: 422 `INVALID_IDENTIFIER`.

## Не сделано
- GraphQL-часть T-F-24 (EC-70 «REST и GraphQL»): GraphQL вне M5.1. T-F-30..32 тоже.
- Нет эндпоинта `GetProductAvailability` (по спеке только GraphQL).
- Тесты, которым нужен Temporal или воркеры, в M5 не писались: сквозная проверка «POST → outbox → relay → проекция» только до записи в БД, проекция в функциональных тестах вызывается напрямую (`projectOutbox()`).

## Отклонения
- `LoggingOrderSagaSignals` вместо `TemporalOrderSagaSignals` (до M6.2). Реализаций `OrderSagaStarter` и `KeyDeliveryNotifier` нет: они не нужны ни одному обработчику HTTP.
- `Currency::values()` (как в спеке `Choice(callback: [Currency::class, 'values'])`) нет в домене, а домен не менялся: `MoneyRequest::currencies()` и `ListCustomerOrdersRequest::statuses()` делают то же из `cases()`.
- `ExceptionToProblemListener` лежит в `Shared/Infrastructure/Http` и импортирует `PriceChanged` из Ordering Domain ради `currentPrice` (infrastructure может зависеть от доменов, T-ARCH не нарушен).
- Функциональные тесты используют `debug: false`: после изменения конфигурации контейнера нужен `rm -rf var/cache/test` (в чистом CI это не проявляется).

## Что проверить вручную
- Живой вызов через nginx (`docker compose up -d`, миграции dev-БД, `POST /api/orders`): тесты идут через `KernelBrowser`, а не через php-fpm/nginx.
- Что `PHP 8.5` deprecation про float-в-int не засоряет логи прода (источник Symfony Serializer).
