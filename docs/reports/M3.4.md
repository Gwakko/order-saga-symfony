# M3.4 Обслуживание и запросы

## Сделано
- Inventory: `ExpireReservations` (по одной транзакции на резервацию, проигравшая гонку по CAS пропускается и не считается), `AddProductKeys` (невалидный код отклоняет весь пакет, дубликаты считаются), `RevokeKey` (EC-18, повтор no-op), запрос `GetProductAvailability` + порт `ProductReadModel`, `ProductAvailabilityOutput`, `Inventory\Application\Exception\ProductNotFound`.
- Payment: `ReconcilePayments` (`olderThanSeconds >= 60`, `limit 1..1000`; `Unknown`/`Abandoned`/`RefundPending` старше порога; поздний успех у заказа в `Failed`/`Cancelled` записывается и возвращается, EC-28; `Unknown` у заказа в процессе остаётся за workflow; отказ шлюза закрывает `Unknown`; сбой шлюза или БД пропускает платёж до следующего запуска).
- Ordering: `GetOrder` и `ListCustomerOrders`, порт `OrderReadModel`, `OrderDetailsOutput`, `OrderSummaryOutput`, `ListCustomerOrdersOutput`, `OrderCursor` (base64url без паддинга, `created_at|order_id`, UTC с микросекундами), `InvalidCursor` (`INVALID_CURSOR`).
- Фейки: `InMemoryOrderReadModel` (владелец, `created_at DESC, order_id DESC`, keyset), `InMemoryProductReadModel`.
- Тесты (44): `InventoryMaintenanceTest`, `ReconcilePaymentsHandlerTest`, `OrderQueriesTest` (группа `M3.4`).
- Проверка: `make phpstan PHP=` OK, `make test-unit PHP=` OK (741 тест), `make ci PHP=` проходит целиком (CS чист).

## Не сделано
- SQL read model (M4.6), по заданию.
- `keyCode` заполняется только для `Completed`: это обязанность SQL-адаптера, у handler проверить нечего (фейк отдаёт то, что в него положили).

## Отклонения от спеки
- `OrderReadModel::list` возвращает `list<OrderSummaryOutput>` вместо `OrderPage`: handler запрашивает `limit + 1`, сам решает, есть ли следующая страница, и кодирует `nextCursor`. Так SQL-адаптеру не нужна логика курсора.
- Курсор задан VO `OrderCursor` (порт принимает его, а не строку), валидация и 422 `INVALID_CURSOR` в Application.
- Валидация диапазонов (`limit`, `olderThanSeconds`, пустой `codes`) сделана в конструкторе Input DTO с `InvalidInput` (`VALIDATION_FAILED`), а не методом `Validate()`: DTO остаются неизменяемыми и невалидное состояние нельзя создать.
- `ReconcilePayments` обрабатывает и `RefundPending` (спека называет `Unknown`/`Abandoned`): иначе возврат, не завершённый из-за недоступного шлюза после завершения workflow, никто бы не довёл.
- `PaymentRepository::findOpenUpdatedBefore` отбирает по `updated_at` (спека: «старше порога»).
- `GetProductAvailability` бросает собственный `ProductNotFound` Inventory (тот же код), а не Ordering (T-ARCH-02).

## Что проверить вручную
- Для M4.6: порядок и сравнение курсора в SQL должны совпадать с `InMemoryOrderReadModel` (кортеж `(created_at, order_id)` строго меньше курсора).
- Для M4.2: индекс/запрос `findOpenUpdatedBefore` по статусам `unknown`, `abandoned`, `refund_pending`.
