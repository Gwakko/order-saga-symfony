# M6.4. Устойчивость воркера

## Сделано

### 1. Переподключение DBAL и сброс сервисов (EC-85)
Код в `src/Saga/Infrastructure/Temporal/Worker/`, подключение в `bin/temporal-worker.php`, сервисы в `config/services.yaml` (public).
- `TransientDatabaseFailure::matches(\Throwable)`: классификатор временных ошибок БД. Признаки: `ConnectionLost`, `ConnectionException`, `RetryableException` (deadlock), SQLSTATE класса `08`, `53`, `57P`, сообщения libpq без SQLSTATE («server closed the connection unexpectedly» и т. п.), проход по цепочке `getPrevious()`. Бизнес-исключения и нарушения ограничений (`23xxx`) временными не считаются.
- `WorkerConnectionGuard`: `ensureAlive()` (если соединение открыто, `SELECT 1`; при временной ошибке `close()`, следующий запрос открывает новое соединение; нетривиальная ошибка зонда пробрасывается), `discard()`, `settle()` (транзакция, оставшаяся открытой после активности, закрывает соединение).
- `ActivityResilienceInterceptor` (`ActivityInboundInterceptor`, регистрируется через `SimplePipelineProvider` в `newWorker(...)`): перед каждой активностью `ensureAlive()`; временная ошибка БД внутри активности: `discard()` и повторный выброс как `ApplicationFailure` типа `TransientDatabaseFailure` с `nonRetryable = false`, то есть Temporal повторяет её по профилю, а не считает бизнес-сбоем. Остальные исключения проходят без изменений (поэтому `non_retryable` по FQCN в `temporal.yaml` работает как раньше).
- `ActivityLifecycle::finish()`: финализатор `registerActivityFinalizer` после каждой активности: `settle()`, затем `services_resetter->reset()` (Monolog и всё с `kernel.reset`). Сброс выполняется даже если `settle()` упал (`finally`).
- Доктриновых сущностей/identity map в проекте нет (только DBAL), кэшей идентичности сбрасывать нечего; своих `ResetInterface`-сервисов в проекте нет.

Перезапись без `getVersion` делает тест бесполезным: он перестанет ловить поломку для уже запущенных экземпляров. Реплей идёт через RoadRunner тестового окружения (RPC 6001), поэтому тест живёт в наборе `workflow`.

### 3. T-I-43 (EC-85)
Тесты `tests/Integration/Worker/WorkerDbReconnectTest` (группы `T-I-43`, `M6.4`). Роль «перезапуска Postgres» из контейнера `php` играет `pg_terminate_backend` по всем сессиям тестовой БД (в контейнере нет docker CLI; для клиента эффект тот же: все сокеты закрыты).
- `testNextActivityReconnectsAfterTheConnectionWasDropped`: соединение убито между активностями; следующая активность через интерцептор выполняется без ошибки на новом соединении.
- `testDropInsideAnActivityIsRetryableAndTheRetryReconnects`: обрыв посреди активности; первая попытка падает как `ApplicationFailure(TransientDatabaseFailure, nonRetryable=false)`, соединение закрыто, повтор успешен.
- `testOrderCompletesAfterTheDatabaseConnectionsAreKilledMidSaga` (`@group slow`, исключена из `make test-int`, запуск `make test-slow`, ~15 с): настоящий воркер (`TemporalTestWorker`), эмулятор держит ответ списания 4 с, во время этого убиваются все сессии БД; проверяется `Completed`, одно списание у шлюза и что в истории есть попытка >= 2.
- **Полуавтоматический скрипт `bin/worker-postgres-restart-check`** (запуск с хоста): настоящий `docker compose restart postgres` под работающей сагой compose-воркера (dev БД, очередь `order-saga`): свежий продукт и ключ, заказ через `POST /api/orders`, старт саги `temporal workflow start`, эмулятор `delay:6000`, рестарт Postgres, опрос статуса.
